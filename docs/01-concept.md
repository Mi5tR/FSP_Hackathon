# ФСП Карьера: концепция решения

Платформа подбора ИТ-специалистов с **обратной механикой**. Кандидат не рассылает отклики: он один раз
проходит обязательный путь (опрос → заявленный грейд → адаптивный тест) и попадает в категорию.
Работодатель описывает потребность обычным текстом, видит подходящие категории и конкретных людей
с объяснением, почему они в подборке, и сам отправляет приглашение, сразу указывая вилку зарплаты.

Веса критериев оценки определяют приоритеты: подбор 35%, тестирование 25%, остальное 40% в сумме.

## 1. Механика контакта (критерий 1, 35%)

| Элемент | Что делает | Зачем |
|---|---|---|
| Потребность свободным текстом | NLP-разбор текста в специализацию, грейд, стек и вилку; работодатель правит результат | Работодатель не обязан знать нашу таксономию |
| Сначала категории, потом люди | Шаг 1 — карточки рекомендованных категорий (точная, соседний грейд Middle ↔ Middle+, смежные специализации) с числом кандидатов, лучшим процентом, долей ФСП, неподтверждёнными и новыми; шаг 2 — кандидаты выбранной категории | Работодатель сначала выбирает категорию, затем человека, как в модели LHH |
| Новые кандидаты | Кто появился в категории потребности после последнего просмотра подборки, отмечен «новый»; счётчик в меню | Работодатель возвращается к подборке, не пересматривая её целиком |
| Ранжирование с объяснениями | Общий процент, откалиброванная вероятность, 6 блоков, покрытие каждого требования и флаги | Требование ТЗ к объяснимости выдачи; один навык не закрывает другой |
| Настраиваемый подбор | Веса блоков, строгость, пороги, жёсткие фильтры с подсчётом отсеянных | Работодатель сам решает, что для него критично |
| Обезличенная карточка | До согласия кандидата видны «Кандидат #N», категория, проверенные навыки, ФСП; ФИО и контакты скрыты | Правило 2.2.2 ТЗ; снижает дискриминацию |
| Зарплатный сигнал без раскрытия | Работодатель видит «ожидания в вилке / выше примерно на X%», но не саму сумму | Кандидат не теряет позицию на переговорах, работодатель не тратит приглашение впустую |
| Фильтр «не ниже моих ожиданий» | Кандидат может запретить приглашения с вилкой ниже своих ожиданий; работодатель получает понятный отказ при отправке | Кандидат не тратит время на заведомо неподходящие предложения |
| Приглашение с обязательной вилкой | Позиция, вилка от и до в рублях, описание, способ связи; привязка к вакансии необязательна | Правило 2.2.1 ТЗ |
| «Почему вас выбрали» | Кандидат видит снимок соответствия: процент, блоки, статус каждого навыка | Прозрачность для обеих сторон; понятно, какой навык подтвердить |
| Лимит приглашений | В сутки: новая компания — 15, средний уровень доверия — 40, высокий — 60; компания на проверке — 0 | Приглашение остаётся ценным, но лимит не мешает нормальному найму |
| Несколько позиций одному кандидату | Можно предложить разные позиции; дубль активного приглашения на ту же позицию запрещён | Работодатель не теряет кандидата, если у него две подходящие роли |
| Срок жизни и статусы | sent → viewed → accepted → **offer** → **hired**; declined (с причиной) / expired (14 дней) / withdrawn | Правило 2.2.3 ТЗ; оффер и выход видны кандидату и синхронизируются с ATS |
| Доверие к работодателю | Кандидат видит оценку 0–100 и сигналы: ИНН, домен почты, доля принятых, ответы после принятия, офферы, жалобы | Защита от недобросовестных работодателей (раздел 5) |
| Жалобы | Кандидат может пожаловаться на приглашение; 3 жалобы разных кандидатов за 30 дней приостанавливают приглашения и вакансии компании | Фиктивные вакансии и «сборщики резюме» быстро теряют доступ |
| Шорт-лист | Отобранные кандидаты сохраняются при смене фильтров | «Уточнение без потери подборки» из ТЗ |
| Отклик (вспомогательный путь) | Кандидат с категорией может откликнуться на опубликованную вакансию, контакты при этом раскрываются | Дополнительный функционал, 7% |
| Переписка по приглашению | Обе стороны пишут друг другу до и после принятия, контакты при этом не раскрываются | Удобнее, чем просто обменяться контактами |
| Отзыв доступа к контактам | После принятия кандидат может отозвать и вернуть доступ; работодатель снова видит обезличенную карточку | Контроль над ПДн у кандидата |
| Неподтверждённый грейд не прячется | Кандидат виден с заявленным грейдом и пометкой «не подтверждён», ниже подтверждённых (штраф ×0.6). Кандидат может сам скрыть профиль до пересдачи | Не выпадает из оборота (ответ постановщиков), выбор остаётся за кандидатом |
| Метка доверия компании | ИНН с корректной контрольной суммой → «ИНН проверен» в приглашении | Добровольная, основной сценарий не блокирует |
| Несовершеннолетние 15–17 лет | Публикация только с согласием законного представителя, работодатель видит «до 18, только лёгкий труд» | 152-ФЗ, ст. 63 ТК РФ |

### Модель релевантности

Релевантность считается в три уровня, и каждый уровень показывается работодателю отдельно.

**Уровень 1. Требования.** Потребность — это список навыков, у каждого есть важность (обязательно или желательно)
и уровень (базовый, уверенный, экспертный). Требования предзаполняются из текста вакансии: «будет плюсом Docker»
даёт «желательно», «глубокое знание SQL» даёт «эксперт». Работодатель их правит. По каждому требованию считается
**покрытие** — вероятность, что кандидат владеет навыком на нужном уровне — и **уверенность** в этой оценке.

Доказательства берутся из нескольких источников с разным доверием:

| Источник | Как учитывается |
|---|---|
| Тест | P(θ_навык ≥ порог уровня) по апостериорной оценке навыка; опорный источник, его вес равен его уверенности |
| Регулярные задания | Оценка работодателя от 1 до 5 по навыкам задания, доверие 0.8 |
| ФСП | Место в соревновании (уровень мероприятия не взвешивается — все соревнования ФСП равнозначны), доверие 0.7 |
| Резюме | Не больше 0.3 и только если нет прямого объективного подтверждения |

* **Граф навыков.** Подтверждение переносится между навыками: FastAPI → Python ×0.8, Python → FastAPI ×0.5,
  Django ↔ FastAPI ×0.35, плюс явные связи (TypeScript ↔ JavaScript, Kotlin ↔ Java).
* **Подкреплённое заявление.** Кандидат указал в резюме «PostgreSQL» и прошёл тест по SQL: заявление подкреплено
  проверенным навыком-родителем и засчитывается ×0.9.
* **Тест главнее остальных источников.** `покрытие = уверенность_теста × тест + (1 − уверенность_теста) × max(тест, другие)`.
  Уверенный провал теста не перекрывается ни ФСП, ни резюме, а при малом числе заданий другие источники честно
  добавляют информацию.
* **Статус требования.** «Подтверждён»; «не закрыт» (прямая проверка показала, что уровня нет, или данных нет совсем);
  «не подтверждён напрямую» (только резюме или косвенный тест). Для последнего кандидату предлагается проверка навыка.

**Уровень 2. Блоки.** Роль (категория из теста: своя — 1.0, соседняя ступень — 0.6, через ступень — 0.25), Стек (покрытие требований), Уровень (запас θ над порогом грейда),
Подтверждённость (доля требований, закрытых объективными источниками), Условия (зарплата и формат), Актуальность.
Каждый блок — число от 0 до 1 с текстовым объяснением. **ФСП — отдельный блок-бонус.**

**Уровень 3. Итоговый процент.**

```
база   = степенное_среднее(блоки, веса, p)        p = 1 — сумма, 0 — геометрическое, < 0 — к минимуму
итог   = база + бонус_ФСП · сила_ФСП · (1 − база)  бонус никогда не уменьшает балл
итог  *= штраф_must ^ (число проваленных обязательных навыков)
итог  *= штраф_непроверенного ^ (число обязательных навыков без прямого подтверждения)
```

Рядом с процентом показывается **откалиброванная вероятность** («≈ 63% таких кандидатов подходят»). Её даёт
изотоническая регрессия, обученная на валидационных данных. На реальных данных она доучивается по действиям
работодателей.

**Всё настраивается в потребности:** веса блоков, строгость p, бонус ФСП, вес желательных навыков, порог
и штраф must-have, штраф за неподтверждённый навык, учёт уверенности в сортировке. Условия по умолчанию мягкие:
кандидат остаётся в выдаче с флагом. Любое из них можно сделать жёстким фильтром (обязательные навыки, вилка,
формат, точный грейд, только ФСП), и выдача покажет, сколько кандидатов скрыл каждый фильтр.

**Значения по умолчанию выбраны по валидации** (раздел 6 в [02-validation.md](02-validation.md)): геометрическое среднее,
порог must-have 0.5 (покрытие — это вероятность, ниже 0.5 «скорее нет»), штраф 0.6 за проваленный обязательный
навык, без учёта уверенности в сортировке: на синтетике он снижал nDCG.

Сортировка: сначала точность категории, внутри неё итоговый балл. Так выполняется требование «внутри категории
выше те, у кого сильнее подтверждённый профиль».

### Проверка навыков из резюме

Навык, указанный в резюме, но не проверенный тестом, весит мало. Кандидат видит список своих навыков со статусами
и количеством вакансий, которым они нужны, и может пройти **короткую проверку навыка** (4–6 заданий). Проверка
адаптивна именно по этому навыку и не меняет грейд. Повтор возможен через 14 дней. Валидация показывает, зачем это
нужно: среди «блестящих» кандидатов без одного обязательного навыка в топ-10 попадают 5–7% тех, кто проверял навык,
и 22–28% тех, кто не проверял.

## 2. Механика тестирования (критерий 2, 25%)

**Справочник.** 8 специализаций: Backend, Frontend, Mobile, Data Science / ML, Аналитик (системный и продуктовый),
QA, DevOps, ИБ. 6 ступеней грейда: Intern, Junior, Junior+, Middle, Middle+, Senior. Грейд — уровень навыков,
подтверждённый тестом, а не стаж. «Отрасль» в опросе — ИТ-направление (разработка, данные, аналитика, качество,
инфраструктура, ИБ).

**Опрос.** Направление и специализация, частые задачи и опросник самооценки из шести утверждений по специализации
(шкала: не делал / с помощью / самостоятельно / учу других). Опросник не присваивает грейд: он питает ML-подсказку
грейда, которую кандидат видит при выборе ступени.

Проблема из ТЗ: единый набор заданий утекает, а генерация уникальных заданий LLM не гарантирует сопоставимую сложность.

**Наш подход: параметрические семейства заданий, откалиброванные по IRT, плюс адаптивное тестирование (CAT).**

1. **Семейство** — это шаблон задачи с генератором. Каждый вариант заново генерирует числа, имена, код и порядок ответов,
   правильный ответ вычисляется программно. Примеры: вывод кода со срезами, LEFT JOIN по заданным данным,
   число попаданий в LRU-кэш, порядок event loop, асимптотика случайной вложенности циклов, подсети, cron.
2. **Калибровка**: у семейства есть параметры 2PL — трудность *b* и дискриминативность *a*. Все варианты семейства
   изоморфны, поэтому сложность сопоставима между кандидатами. Именно это LLM-генерация «на лету» не обеспечивает.
3. **Адаптивность**: старт с априорной оценкой по заявленному грейду, затем задание с максимумом информации Фишера
   в текущей оценке θ; выбор случайный из топ-4 для контроля экспозиции; не более двух заданий подряд на один навык.
   Остановка при SE ≤ 0.30 либо на 22 заданиях (минимум 12); общий лимит теста — 20 минут.
4. **Решение о грейде** принимается по апостериорной вероятности P(θ ≥ порог), а не по проценту верных:
   * P ≥ 0.5 (медиана апостериорного распределения не ниже порога) — грейд подтверждён. Для полос шириной 0.5
     это несмещённое решение; порог 0.6 давал систематическое занижение (подобрано по валидации);
   * дополнительно P(θ ≥ следующий порог) ≥ 0.8 — «подтверждён уверенно»: система сама предлагает отдельный тест
     на ступень выше, и он доступен сразу, без ожидания 90 дней. Автоматического повышения нет;
   * иначе «не подтверждён». Грейд **не понижается принудительно**, предлагается тест на уровень ниже (доступен сразу).
     Если подтверждённого грейда ещё нет, кандидат **не скрывается**: в выдаче он виден с заявленным грейдом
     и статусом «не подтверждён», ниже подтверждённых кандидатов своей категории.
5. **Правила**: грейд кандидат выбирает сам (ML-модель только подсказывает по стажу, стеку, ФСП и опроснику); смена
   подтверждённого грейда не чаще раза в 90 дней; повтор того же уровня после неудачи через 30 дней, тест на уровень
   ниже — сразу, попытка не сгорает; ответ после истечения лимита времени не засчитывается; правильный ответ никогда
   не уходит на клиент.
5a. **Вес «знаниевых» заданий.** У семейств с малым числом уникальных формулировок (меньше 250 из 300 вариантов)
   ответ легко слить, поэтому в оценке θ их дискриминативность умножается на 0.5. На атаке «слитый ключ» это снизило
   долю слабых кандидатов, прошедших на Middle, с 37% до 16% при почти неизменной точности грейда.
5b. **Честность прохождения**: копирование условия заблокировано; уходы с вкладки, попытки копирования и подозрительно
   быстрые ответы фиксируются и показываются работодателю сводкой («тест пройден чисто / есть сигналы»). На оценку θ
   они не влияют, чтобы случайный уход с вкладки не стоил грейда.
6. **Роль LLM** — только офлайн: LLM предлагает новые *семейства* (шаблон и генератор). Семейство попадает в банк
   как pretest-задание без влияния на грейд, калибруется на ответах и только потом становится рабочим.
7. **Мониторинг утечки** (следующий этап): если доля верных ответов по семейству растёт быстрее, чем предсказывает модель
   при текущих θ отвечающих, это сигнал на ротацию семейства (дрейф параметров).
8. **Профиль навыков**: по каждому навыку считается своя оценка θ_навык с неопределённостью, стянутая к общему
   уровню кандидата (partial pooling): мало заданий — оценка близка к общему уровню и уверенность низкая.
   Адаптивный выбор заданий учитывает покрытие навыков: пока по навыку меньше двух заданий, его семейства
   получают приоритет. У каждого ключевого навыка в банке есть задания нескольких уровней сложности, иначе провал
   средних заданий не отличает «не знает основ» от «не дотягивает до middle».
9. **Тест под вакансию**: категорийный тест одинаков по структуре, вакансия только смещает приоритет семейств
   на свой стек (вкладка «Как тестируем кандидатов» показывает состав и пример варианта).

Регулярные короткие задания от работодателей обновляют актуальность профиля и дают работодателю свежий сигнал.
Задания с эталоном проверяет система, открытые («предложите подход») оценивает работодатель по шкале от 1 до 5.
Задания адресные: система сама выбирает для кандидата одно «задание для вас» — по навыку, где в его профиле меньше
всего данных, — и показывает счётчик новых заданий в меню.

## 3. Валидация (часть критерия 2)

Эталонной разметки нет, поэтому мы генерируем популяцию с **известной истиной** (способность θ, специализация,
навыки), 30% кандидатов завышают грейд, 30% резюме приукрашены. Эта популяция проходит через **реальный код**
тестирования и подбора. Отчёт: [02-validation.md](02-validation.md), команда `python -m scripts.validate`.

У каждого кандидата своя способность по каждому навыку (общий θ плюс сдвиг навыка), поэтому эталон «владеет
навыком на требуемом уровне» согласован с тем, как кандидат отвечает на задания.

Измеряем:
* по тесту: точность грейда и матрицу ошибок, повторное прохождение (каппа Коэна), точечно-бисериальную корреляцию
  по семействам, атаку «слитый ключ» в сравнении с фиксированным тестом, устойчивость к ошибке калибровки;
* по подбору: precision@10, strict precision@10 и nDCG@10 в сравнении с keyword-бейзлайном и «оракулом»;
  долю кандидатов в топ-10 без обязательного навыка; **стресс-тест компенсации** («блестящие» кандидаты без одного
  обязательного навыка) отдельно для проверивших и не проверивших навык; **калибровку процента** (ECE до и после
  изотонической регрессии, обучение и проверка на разных половинах кандидатов);
* **абляцию**: одни и те же данные прогоняются через разные способы агрегации (сумма, геометрическое среднее,
  штрафы, учёт уверенности, строгий режим), чтобы показать вклад каждого механизма и обосновать значения по умолчанию.

Эталонная разметка — истина по построению: у каждого синтетического кандидата известны уровень, специализация
и навыки, а релевантность пары «потребность — кандидат» задаётся правилами эксперта, независимыми от ранжирования.
Это и есть «эталонная разметка команды», которую допускают постановщики.

Следующий шаг: 10–20 живых респондентов с известным уровнем (коллеги и участники ФСП) проходят тест дважды.
Это даст реальную оценку повторного прохождения и сравнение с экспертной оценкой грейда.

## 4. ФСП

Профиль связывается с ФСП ID через вход по OIDC (Authorization Code). В демо работает имитация Keycloak, в продакшене —
Keycloak ФСП (переключается переменными окружения). `sub` токена и есть ФСП ID, поэтому привязать чужой ID нельзя.
Схемы потоков и правила учёта достижений — [06-fsp-integration.md](06-fsp-integration.md).

Все соревнования ФСП учитываются одинаково по престижу, но учитывается профильность дисциплины для специализации
(идея постановщиков: ИБ-специалисту CTF релевантнее робототехники; коэффициент от 0.6 до 1.0). Уровень мероприятия
не взвешивается, считаются число стартов
и результативность (победа > призовое место > топ-10 > участие), вклад одних участий ограничен, свежие
результаты весят больше. Грейд достижения не меняют. Предлагаемый контракт реестра и данные, которые полезно показывать работодателю:
мероприятие, дисциплина, уровень (региональный, всероссийский, международный), дата, место и число участников,
роль в команде, навыки, ссылка на протокол. Случай «истории нет» обрабатывается явно.

## 5. Защита от фиктивных вакансий и интеграция с ATS

Верификация компании на этапе MVP не обязательна (п. 2.2.4 ТЗ), поэтому защита строится на поведении: каждое
действие работодателя оставляет след, который видит кандидат. Реализовано (`app/services/trust.py`):

* **Метки доверия:** ИНН с корректной контрольной суммой; почта компании на домене её сайта.
* **Оценка доверия 0–100** из сигналов: возраст аккаунта, доля принятых приглашений за 90 дней, доля ответов
  в переписке после принятия (защита от «гостинга»), офферы и выходы на работу, жалобы.
* **Лимит приглашений в сутки** зависит от уровня: новая компания 15, средний уровень 40, высокий 60.
* **Жалобы кандидатов** (сбор резюме, просьба об оплате, несовпадение условий, спам, некорректное общение):
  3 жалобы разных кандидатов за 30 дней переводят компанию в статус «на проверке» — приглашения и вакансии
  приостанавливаются. В демо так выглядит компания «Карьерный Старт Плюс».
* **Вилка-приманка:** если верх вилки в 1.8 раза выше медианы ожиданий кандидатов категории, кандидат видит
  предупреждение.

Следующий этап: сверка ИНН с ЕГРЮЛ/ФНС, ручная модерация жалоб, эскроу-вилка (вилку из принятого приглашения нельзя
снизить на первом интервью без объяснения).

**Интеграция с ATS — Huntflow API v2** (`app/integrations/ats.py`, `app/services/ats_sync.py`). Работодатель
подключает аккаунт в профиле компании (без токена — демо-режим без сети):
* платформа → ATS: когда контакты раскрыты (принято приглашение или отклик), кандидат создаётся в Huntflow
  и добавляется на вакансию; оффер, выход и отказ передаются этапом;
* ATS → платформа: вебхук `/api/integrations/huntflow/webhook/{secret}` о смене этапа («Оффер», «Вышел на работу»,
  «Отказ») обновляет статус приглашения, кандидат видит его у себя; переходы только вперёд по воронке;
* вакансии из ATS импортируются черновиками потребностей. Чужие площадки не парсятся — это вакансии самого
  работодателя;
* журнал синхронизации виден работодателю; персональные данные уходят в ATS только после раскрытия контактов.

## 6. ML и NLP

Без GPU и внешних API, на scikit-learn (`app/services/ml.py`):
* **Специализация по тексту резюме** — TF-IDF символьных n-грамм и логистическая регрессия; подсказка в опросе
  и при разборе PDF и описания вакансии. Категорию модель не присваивает.
* **Нечёткое распознавание навыков** — опечатки и транслит («Постгрес», «Кубернетес», «Typscript»); найденное
  помечается «распознано по сходству», работодатель добавляет навык одним нажатием.
* **Подсказка грейда** — мультиклассовая логистическая регрессия по стажу, ширине стека, призовым местам ФСП
  и опроснику самооценки; кандидат видит распределение вероятностей по ступеням.
* **Калибровка процента релевантности** — изотоническая регрессия (раздел 1).

Качество на отложенной синтетике — раздел 7 в [02-validation.md](02-validation.md). Облачные LLM допустимы, но
в обязательный путь не входят: персональные данные никуда не передаются, стенд проверки работает без GPU.
